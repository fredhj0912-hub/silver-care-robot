# 파이 당일 실행 순서 (런북)

라즈베리파이 5 앞에서 **위에서부터 그대로 따라가는** 문서다.
배경·이유·되돌리기는 여기 적지 않는다 — `docs/deploy-raspberry-pi.md`(레퍼런스)에 있다.

각 단계 머리의 라벨이 **어느 기기에서 치는 명령인지**를 뜻한다:

| 라벨 | 기기 |
|---|---|
| `[개발 PC]` | 윈도우 노트북 (레포가 있는 곳) |
| `[파이]` | 라즈베리파이 5의 터미널 |
| `[폰]` | 보호자 앱을 여는 휴대전화 |
| `[EC2]` | 개발 PC에서 SSH로 들어간 서버 |
| `[콘솔]` | 브라우저로 연 AWS 콘솔 (CloudShell / Instance Connect) |

> **§0~§7은 2026-09-01에 파이 5에서 실제로 돌려 가며 고친 문서다.**
> **§3-B(화면 회전)와 §6-3(음성 인식)은 09-02에 새로 쓴 것이라 아직 실측이 아니다.**
> **§8(낙상)·§9(구동부)도 실측이 아니다** — 09-01에 거기까지 가지 못했다.
> 각 단계의 **"성공한 모습"** 을 보고 넘어가고, 안 되면 그 자리에서 §10을 본다.

## 0-A. 🔴 평소와 다른 와이파이라면 — 먼저 이것부터 `[개발 PC]` `[콘솔]`

**EC2의 SSH(22번)는 개발 PC의 공인 IP 하나에만 열려 있다.** 그래서 다른 네트워크로 옮기면
아래 두 가지가 **전부 막힌다**:

- §0의 `npm run access` (내부적으로 EC2에 SSH한다)
- §8-4의 `mock-detector` (EC2에 들어가야 한다)

**증상이 "연결 거부"가 아니라 타임아웃**이라 원인을 찾는 데 시간을 버리기 쉽다.
파이와 폰은 영향이 없다 — 터널 주소로 밖으로 나가기만 하므로 어느 네트워크든 된다.

**대응 1 — 새 IP를 보안 그룹에 추가한다 (권장)**

먼저 개발 PC에서 지금 공인 IP를 확인한다:

```powershell
curl.exe -s https://checkip.amazonaws.com
```

그다음 **AWS 콘솔 → CloudShell**을 열고(이 계정은 액세스 키 발급이 불가능하므로
로그인 세션을 그대로 쓰는 CloudShell이 유일한 CLI 경로다):

보안 그룹 ID를 모르면 인스턴스로 찾는다(퍼블릭 IP도 같이 나온다):

```bash
aws ec2 describe-instances --region us-west-2 --instance-ids <인스턴스 ID> \
  --query 'Reservations[].Instances[].{IP:PublicIpAddress,SG:SecurityGroups[].GroupId}'
```

그다음 22번을 연다:

```bash
aws ec2 authorize-security-group-ingress --region us-west-2 \
  --group-id sg-XXXXXXXX \
  --ip-permissions 'IpProtocol=tcp,FromPort=22,ToPort=22,IpRanges=[{CidrIp=<확인한 IP>/32,Description="dev-pc"}]'
```

> ⚠️ **`<`와 `>`는 자리표시자다 — 지우고 값만 넣는다.** 그대로 두면 셸이 리다이렉션으로
> 읽어 `No such file or directory`가 난다(09-01에 실제로 겪었다).
> 이미 열린 IP면 `InvalidPermission.Duplicate`가 나는데, **이미 됐다는 뜻**이니 넘어간다.

> ⚠️ CloudShell 안에서 `checkip`을 부르면 **CloudShell의 IP**가 나온다. 반드시 개발 PC에서
> 확인한 값을 넣을 것.

**대응 2 — SSH를 아예 쓰지 않는다**

콘솔의 **EC2 Instance Connect**(브라우저 SSH)는 AWS 대역으로 열려 있어 **어느 네트워크에서든
접속된다.** 거기서 터널 주소를 직접 읽으면 §0을 건너뛸 수 있다:

```bash
journalctl -u cloudflared.service --no-pager -o cat \
  | grep -oE 'https://[a-z0-9-]+\.trycloudflare\.com' | tail -1
```

`mock-detector`(§8-4)도 같은 창에서 실행하면 된다.

> 보안 그룹 ID·현재 열린 IP 같은 값은 **공개 레포라 여기 적지 않는다.** 콘솔에서 확인한다.
> 로컬에서 RDS에 직접 붙는 작업(`npm run dev`, `verify-rds`)도 같은 이유로 막히지만,
> 내일 순서에는 없다.

## 0-B. 🔴 EC2에 최신 코드를 올린다 `[EC2]`

**이 단계를 건너뛰면 §3 이후의 검증이 전부 무효다.** 파이는 EC2가 서빙하는 번들을 받으므로,
EC2가 옛 코드면 **파이에서 확인하는 것도 옛 화면**이다. 09-01에 이 단계가 문서에 없어서
따로 챙겨야 했다.

```bash
cd ~/silver-care-robot
git fetch origin && git checkout <배포할 브랜치> && git pull
git log --oneline -1        # ← 이 확인이 핵심이다
```

> ⚠️ **브랜치부터 확인한다.** `git pull`만으로는 다른 브랜치의 변경이 오지 않는다.
> 과거에 "EC2가 `main`보다 14커밋 뒤에 있어서 `.env` 두 줄인 줄 알았던 일이 재빌드였다"는
> 사고가 있었다.

`VITE_*` 값은 **빌드 시점에 번들에 박히므로** `.env`를 먼저 손대고 빌드한다:

> 🔴 **09-02 변경분(서버측 STT + 말풍선 크기)은 프론트엔드 번들에 들어 있다.**
> `npm run build`를 건너뛰면 파이는 옛 화면을 계속 받는다 — 음성도 09-01처럼 실패한다.
> `VITE_STT_MODE`는 비워 두면 `server`가 기본이라 따로 넣을 필요는 없다.

```bash
grep VITE_VISION frontend/.env         # 카메라를 쓸 것이면 true 여야 한다
cd frontend && npm run build
sudo systemctl restart hyodol.service
systemctl is-active hyodol.service cloudflared.service
```

**성공한 모습**: `active`가 **두 줄**.

> `cloudflared`를 재시작하지 않으면 **터널 주소는 그대로다.** 주소가 유지되면 §8-3의
> 푸시 재구독을 건너뛸 수 있으므로, 굳이 함께 재시작하지 않는다.

## 0. 서버 주소 확보 `[개발 PC]`

파이는 EC2가 서빙하는 화면을 여는 브라우저일 뿐이다. **서버 주소부터 확보한다.**

```bash
cd <레포 폴더>
npm run access -- <EC2 퍼블릭 IP>
```

**성공한 모습**: `ACCESS.html 갱신 완료`와 함께 두 주소가 출력된다.
```
📺 라즈베리파이 : https://<터널 주소>/
📱 휴대전화     : https://<터널 주소>/guardian
상태: 백엔드 active / 터널 active / 헬스체크 ok
```

이 **터널 주소를 적어 둔다.** 3번에서 파이에 입력한다.

- 접속 실패 → 인스턴스를 stop/start해서 **퍼블릭 IP가 바뀐 것**이다(reboot은 안 바뀜).
  AWS 콘솔에서 새 IP를 확인해 다시 실행한다.
- `상태: ... inactive` → EC2에 SSH로 들어가 `sudo systemctl start hyodol cloudflared`.
- **터널 주소가 어제와 다르면 폰의 푸시 구독을 다시 해야 한다** — 브라우저는 다른 주소를
  다른 사이트로 취급한다. §8에서 처리한다.

## 1. 파이 준비 `[파이]`

### 1-0. 먼저 파이에 접속한다

> **`[파이]` 라벨은 "그 명령이 파이에서 실행된다"는 뜻이다.** 노트북에서 `git clone`하면
> 파일이 노트북에 받아지고 파이에는 아무것도 안 생긴다.
> **노트북에서 SSH로 접속하면, 그 창의 셸은 파이에서 도는 것이므로 맞다.**

```powershell
ssh <파이 사용자>@<파이 호스트명>.local     # 예: ssh pi@raspberrypi.local
```

- **호스트명을 짐작하지 말 것.** 파이 OS 기본값은 보통 `raspberrypi`지만, 09-01에 쓴 기기는
  `pi`였다(따라서 `ssh pi@pi.local`). 파이에서 `hostname`으로 확인한다.
- `.local`(mDNS)이 안 되면 파이 IP를 직접 쓴다 — 파이에서 `hostname -I`.
- **파이에서 SSH가 켜져 있어야 한다**: `sudo raspi-config` → Interface Options → SSH.
  (파이 OS는 기본으로 꺼져 있는 경우가 많다. 이건 파이에 직접 키보드를 붙여 한 번만 하면 된다.)
- 노트북과 파이가 **같은 와이파이**에 있어야 한다.

**제대로 붙었는지 확인** — 파이면 `aarch64`가 나온다:

```bash
hostname && uname -m
```

### ⚠️ SSH로는 안 되는 것 — 미리 알아 둘 것

대부분은 SSH로 되지만 아래는 예외다. 모르면 **정상 동작을 고장으로 오해한다.**

| 단계 | SSH에서 | 어떻게 |
|---|---|---|
| §4 사전점검의 **컴포지터** 항목 | `XDG_SESSION_TYPE=(없음)` 경고가 뜬다 | **정상이다.** SSH 세션에는 그래픽 환경이 없다. 컴포지터 자체는 `pgrep`으로 잡히므로 결과는 유효하다 |
| §4의 **스피커·마이크** | 대개 되지만 장치 권한에 따라 실패할 수 있다 | 실패하면 파이 앞에서 직접 실행 |
| §5 `sudo reboot` | **SSH 연결이 끊긴다** | 정상이다. 30~60초 뒤 다시 `ssh` |
| §6 화면·소리·음성 | 확인 자체가 불가능 | **파이 모니터를 눈으로, 스피커를 귀로** 확인해야 한다 |
| §10의 수동 `./kiosk.sh` | 디스플레이가 없어 실패한다 | **파이 데스크톱의 터미널에서** 실행 |

즉 **§1~§5는 노트북에서 SSH로 편하게 하고, §6부터는 파이 화면 앞에 서서** 하면 된다.

### 1-1. 설치와 clone

파이가 인터넷에 연결된 상태에서 시작한다(clone을 해야 하므로).

**한 줄씩 따로 실행한다.** 어디서 실패했는지 바로 보이고, 뒤 명령이 조용히 건너뛰어지지 않는다.

```bash
sudo apt update
sudo apt install -y chromium-browser git curl alsa-utils wlr-randr
```

> 최신 파이 OS는 패키지 이름이 `chromium`이다. `chromium-browser`를 못 찾는다고 하면
> `sudo apt install -y chromium git curl alsa-utils wlr-randr`.
>
> `wlr-randr`는 **화면 방향**을 돌리는 데 쓴다(§3-B). 09-01에 화면이 세로로 떴다.

```bash
git clone https://github.com/fredhj0912-hub/silver-care-robot.git
```

**이미 `silver-care-robot` 폴더가 있으면** (예전에 받아 둔 경우) clone은 실패한다.
지우지 말고 최신으로 맞춘다:

```bash
cd ~/silver-care-robot
git status --short          # 손댄 파일이 있으면 먼저 확인한다
git fetch origin
git checkout feat/pi-deployment
git pull
git log --oneline -1        # 개발 PC에서 푸시한 커밋과 같은지 눈으로 확인한다
```

> 🔴 **`main`이 아니라 `feat/pi-deployment`다.** `deploy/pi/`는 이 브랜치에만 있다.
> `main`으로 옮기면 스크립트 폴더가 통째로 사라진다. (09-02에 이 문서가 시킨 대로
> 했다가 실제로 겪었다 — 이전 판에는 `git checkout main`이라고 적혀 있었다.)

> 🔴 **`git pull`이 조용히 실패할 수 있다.** 파일을 손댄 적이 있으면
> `error: Your local changes ... would be overwritten` 로 **중단**되는데, 그다음 명령을
> 그대로 이어 치면 **옛 버전으로 작업하게 된다.** `git log --oneline -1`을 꼭 볼 것.
>
> 막히면 먼저 무엇이 바뀌었는지 본다 — `git diff deploy/pi/`.
> `old mode`/`new mode` 뿐이면 `chmod +x` 흔적이라 버려도 된다:
>
> ```bash
> git checkout -- deploy/pi/ && git pull
> ```
>
> 실제 코드가 바뀌어 있으면 버리지 말고 `git stash` → `git pull` → `git stash pop`.

```bash
cd ~/silver-care-robot/deploy/pi
ls -l *.sh                  # 앞에 x가 보여야 한다
```

> 09-02부터 실행 권한이 git에 들어 있어 `chmod +x`는 필요 없다. 예전에는 파이에서
> `chmod`를 하면 그게 로컬 수정으로 남아 **다음 `git pull`을 막았다** — 실제로 겪었다.
> 혹시 x가 안 보이면 `chmod +x *.sh` 후 `git update-index --chmod=+x` 로 레포에도 반영할 것.

**node도 npm도 설치하지 않는다.** 파이에서는 아무것도 빌드하지 않는다.

**성공한 모습**: `ls`에 `kiosk.sh install-autostart.sh set-url.sh set-rotation.sh preflight.sh wifi-setup.sh`가 보인다.

## 3-B. 🔴 화면 방향 `[파이]`

09-01에 화면이 **세로로** 떴다. 키오스크는 800×480 **가로**를 전제로 만들었다 —
세로로 뜨면 얼굴·말풍선·SOS 버튼 배치가 통째로 어긋난다.

```bash
./set-rotation.sh              # 먼저 지금 상태를 본다 (출력 이름 + transform)
./set-rotation.sh 90           # 90 / 180 / 270 중 맞는 값을 찾는다
```

화면을 보고 맞으면 `y`를 눌러 저장한다. 저장하면 `~/.config/hyodol/kiosk.env`의
`KIOSK_ROTATE`에 들어가고 **부팅 때마다 `kiosk.sh`가 적용한다.**

**성공한 모습**: `wlr-randr` 출력이 `800x480` + 원하는 `transform`이고, 화면이 가로다.

> 🔴 **터치스크린이면 여기서 끝이 아니다.** 화면을 돌린 뒤 **터치가 맞는 자리에
> 눌리는지** 반드시 확인한다 — 화면만 돌고 터치 좌표는 안 도는 것이 흔한 함정이다.
> 화면 아래쪽 텍스트 입력칸을 눌러 커서가 거기 생기는지로 확인하면 된다.
> 안 돌아가면 컴포지터 설정에서 입력 장치를 출력에 매핑해야 한다(labwc/wayfire 문서).

> **CSS로 돌리지 말 것.** `transform: rotate()`는 그림만 돌리고 터치 좌표는 그대로
> 두기 때문에, 화면은 멀쩡해 보이는데 엉뚱한 곳이 눌린다. 어르신이 쓰는 화면에서
> 이것은 고장보다 나쁘다 — 눌리기는 눌리는데 다른 게 눌린다.

## 4. 사전 점검 `[파이]`

```bash
./preflight.sh
```

기기 → 그래픽 세션 → 네트워크 → **백엔드 연결** → 스피커 → 마이크 → 카메라 → Chromium
순으로 확인한다. 중간에 스피커에서 440Hz 소리가 나므로 **귀로 확인**한다.

**성공한 모습**: 마지막 줄이 `자동 점검 통과`.

**❌가 하나라도 있으면 여기서 멈추고 고친다.** 앱을 의심하기 전에 하드웨어부터다.
가장 자주 틀리는 것은 4번(백엔드 연결) — 터널 주소가 낡은 경우다.

> SSH로 실행하면 2번(그래픽 세션)에 `XDG_SESSION_TYPE=(없음)` 경고가 뜬다. **정상이다** —
> SSH 세션에는 그래픽 환경이 없다. 컴포지터 자체는 `pgrep`으로 잡으므로 결과는 유효하다.

> 6번(마이크)에서 출력되는 **기본 장치 이름**을 꼭 본다. Chromium은 권한 대화상자를
> 자동 수락하면서 **기본 장치**를 말없이 집는다. USB 마이크가 기본이 아니면
> 소리를 못 듣는데도 화면에는 아무 오류가 안 뜬다.

> 🔴 5번은 **경고 문구가 아니라 "기본 출력" 줄을 읽는다.** 09-02에 스크립트가
> `Sinks:` 구획을 못 끊고 마이크의 기본 장치까지 함께 집어 "기본 출력이 마이크입니다"
> **오탐**을 냈다(고쳤다). 출력이 두 줄로 나오면 그 버그가 남아 있는 것이다.
>
> `speaker-test 실행 실패`도 **스피커 고장이 아니다.** ALSA `default`가 파이에서는
> HDMI로 잡혀 있어 USB 스피커를 쓰면 실패한다. 소리 확인은 `pw-play`로 한다
> (스크립트도 09-02부터 그렇게 바뀌었다).
>
> 🔴 5번의 **기본 출력**도 함께 본다. 09-01에 USB 마이크 어레이(reSpeaker)가 **기본 출력을
> 가로채** 로봇이 말을 해도 아무 소리가 안 났다. `speaker-test`는
> `Playback open error: -524`만 뱉어서 원인을 알 수 없다. 고치는 법:
>
> ```bash
> wpctl status            # Sinks 목록에서 진짜 스피커의 ID를 찾는다
> wpctl set-default <스피커 ID>
> wpctl set-volume <스피커 ID> 0.8
> pw-play /usr/share/sounds/alsa/Front_Center.wav   # 여기서 소리가 나야 한다
> ```
>
> 한 번 바꾸면 재부팅해도 유지된다(실측). 바꾼 뒤에는 **키오스크를 재시작**해야
> Chromium이 새 출력을 잡는다 — `pkill -f 'chromium.*--kiosk'` (감시 루프가 3초 뒤 다시 띄운다).

## 6. 화면 · 소리 · 음성 `[파이]` `[폰]`

**순서가 중요하다.** 소리를 먼저 확인해야 음성 실패의 원인을 좁힐 수 있다.

**6-1. 화면** — 얼굴이 뜨고 800×480에 맞게 들어갔는가. 얼굴 아래 **상태 줄**을 읽는다.

**6-2. 소리** `[폰]` — 폰에서 `https://<터널 주소>/guardian/send` 를 열고 아무 말이나 보낸다.

**성공한 모습**: 파이 스피커에서 그 말이 나오고, 화면에 `보호자님 메시지: …`가 뜬다.
왕복은 **5초 안팎**이다(09-01 실측 — 폴링 대기 + 음성 생성 + 터널 전송이 합쳐진 값).

> 🔴 **화면에 글은 뜨는데 소리만 안 나면**, 순서대로 좁힌다:
>
> 1. `pw-play /usr/share/sounds/alsa/Front_Center.wav` — **안 나면 출력 장치 문제다**(§4의 5번).
> 2. 소리가 나는데 로봇만 조용하면 **TTS 엔진 문제다.** 기본값 `TTS_PROVIDER=browser`는
>    리눅스에서 `speech-dispatcher`가 있어야 하고, 있어도 한국어 보이스가 없으면
>    **아무 소리 없이 조용히 실패한다.** 09-01에 실제로 이 경우였다.
> 3. 해결은 **서버측 TTS**다. EC2의 `backend/.env`에 `TTS_PROVIDER=gemini`를 넣고
>    `sudo systemctl restart hyodol.service`. 브라우저 음성 엔진이 아예 필요 없어지고
>    목소리 품질도 낫다. `npm run prewarm-tts`로 자주 쓰는 문장을 미리 캐싱해 둔다.
>    (`.env`에 그 줄이 아예 없을 수 있다 — `grep TTS_PROVIDER .env`로 먼저 확인할 것.)

**6-3. 음성 인식** `[파이]` — 파이 앞에서 **"효돌아"** 하고 부른다.

> **09-02부터 받아쓰기는 서버가 한다.** 브라우저(Chromium)가 아니라 파이가 마이크를
> 직접 녹음해 EC2로 보내고 Gemini가 받아쓴다. 09-01에 실패한 Chromium 음성 인식은
> 이제 쓰지 않는다 — 그 빌드에 구글 음성 키가 없다는 사실은 그대로다.
>
> 그래서 **말을 마치고 잠깐 기다려야 한다.** 발화가 끝난 것을 감지(0.9초 침묵) →
> 업로드 → 받아쓰기 → 대답 생성 → 음성 합성이 차례로 일어난다.

**성공한 모습**: 말을 마치고 잠깐 뒤 상태 줄이 `생각하는 중...`으로 바뀌고 로봇이 대답한다.

**상태 줄이 곧 진단 메시지다:**

| 화면 문구 | 뜻 | 조치 |
|---|---|---|
| `"효돌아" 하고 불러주세요` | 정상 — 마이크가 살아 있다 | 다음으로 |
| `안전하지 않은 주소로 열렸어요 (HTTPS 필요)` | http로 열렸다 | `./set-url.sh`로 https 주소를 넣는다 |
| `마이크를 쓸 수 없어요` | 권한 거부 또는 입력 장치 없음 | §4의 6번(기본 입력 장치)을 다시 본다 |
| `음성 인식 서버에 닿지 않아요` | **EC2/터널에 못 닿는다** (뜻이 09-01과 달라졌다) | §0으로 — 터널 주소가 낡았거나 EC2가 죽었다 |
| `아래에 글로 말씀해 주세요` | 백엔드가 받아쓰기를 못 한다(503) | EC2의 `GEMINI_API_KEY` 확인 |

**막히면 어디서 끊겼는지부터 가른다** — 세 구간 중 하나다:

1. **마이크가 안 잡힌다** → 상태 줄이 `마이크를 쓸 수 없어요`. §4의 6번에서 **기본 입력
   장치**를 확인한다. Chromium은 권한을 자동 수락하면서 **기본 장치**를 말없이 집는다.
2. **말해도 아무 반응이 없다** → 소리가 임계값에 안 닿는 것이다. 조금 더 크게, 마이크에
   가까이서 말해 본다. 그래도 안 되면 `VITE_STT_MODE`/VAD 임계값 조정이 필요하다
   (`frontend/src/lib/vad.js`의 `startThreshold`).
3. **받아쓰긴 하는데 엉뚱하게 알아듣는다** → 정상 범위다. 로봇이 되묻게 돼 있다.

> **로봇이 자기 목소리에 반응하지 않는지** 함께 본다. 로봇이 말하는 동안에는 녹음이
> 멈추게 돼 있다(`isSpeakingRef`). 혼자 계속 대답을 이어 가면 그 게이트가 풀린 것이다.

> **다른 입력 경로**(서버 STT가 안 될 때):
>
> | 입력 | 상태 |
> |---|---|
> | 음성 ("효돌아") | 서버측 STT — **이번에 확인할 것** |
> | 화면 텍스트 입력 | ⚠️ 파이에 가상 키보드가 없다 — 물리 키보드가 필요하다 |
> | 폰 보호자 앱 `/guardian/send` | ✅ 09-01 동작 확인 |

## 9. 구동부 확인 `[파이]`

**정직하게 말하면, 이 레포에는 모터 제어 코드가 없다.** `backend/src/services/motion.js`는
메모리에 가상 좌표만 유지하는 시뮬레이터다. "예전에 움직인 적 있다"는 그때 쓰던 **별도 코드**다.

그래서 오늘 할 일은 **무엇이 어떻게 붙어 있는지 파악하는 것**까지다.

```bash
pinctrl get                 # Bookworm (예전 raspi-gpio 대체)
gpioinfo 2>/dev/null | head -40
ls /dev/i2c-* 2>/dev/null
i2cdetect -y 1 2>/dev/null  # 모터 HAT이 I2C면 여기 주소가 뜬다
```

확인할 것:
- [ ] 구동부가 파이 GPIO/I2C에 **물리적으로 연결돼 있는가**
- [ ] 예전에 쓰던 제어 코드/라이브러리가 어디 있는가 (다른 레포? SD카드? 팀원?)
- [ ] 모터 드라이버 종류 (L298N / 모터 HAT / 서보 등)

**다음 단계의 방향만 적어 둔다** (오늘 만들지 않는다):
찾은 제어 코드를 `GET /api/commands/pending?kind=move&maxAgeMs=2000` 를 폴링해서
실행하고 `POST /api/commands/:id/ack` 하는 프로세스로 감싸면 된다.
**`move`를 ack하는 것은 이 프로세스 하나뿐이어야 한다** — 키오스크는 보기만 하도록
이미 바꿔 두었다.

| 상태 줄에 `음성 인식 서버에 닿지 않아요` | **EC2/터널에 못 닿는다** (09-01의 Chromium STT 실패와는 다른 뜻이다) | §0으로 — 터널 주소 갱신 |
| 상태 줄에 `아래에 글로 말씀해 주세요` | 백엔드가 받아쓰기 불가(503) | EC2의 `backend/.env`에서 `GEMINI_API_KEY` 확인 |
| **로봇이 자기 말에 계속 대답한다** | 발화 중 녹음 정지 게이트가 풀렸다 | 스피커 볼륨을 낮춰 본다. 재현되면 `isSpeakingRef` 경로를 본다 |
| **연타해도 이동 표시가 안 뜬다** | 의도된 동작 — 이전 요청 중 연타 무시(`ControlScreen.jsx`) + 2초 넘은 명령은 조회에서 제외 | 천천히 한 번씩 누른다 |
| 원격조종이 안 먹음 (`423`) | **응급 상태로 잠김** | 폰에서 알림을 해제한다 (§8-5) |
| 인터넷은 되는데 화면이 안 열림 | 캡티브 포털 | 폰 핫스팟을 켠다 |
| 파이 IP를 몰라 SSH 못 함 | 네트워크마다 IP가 바뀜 | `ssh <사용자>@<호스트명>.local` (mDNS). **호스트명은 기기마다 다르다** — 파이에서 `hostname`, 안 되면 `hostname -I` |
| SSH 접속 자체가 안 됨 | 파이에서 SSH가 꺼져 있음 | 파이에 키보드를 붙여 `sudo raspi-config` → Interface Options → SSH |

되돌리기는 `docs/deploy-raspberry-pi.md` §7.
